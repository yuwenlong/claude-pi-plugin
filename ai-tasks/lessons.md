# 经验教训

## 2026-08-27 · "参考 X 实现类似功能"不等于"照搬 X 的形态"

**圣上的修正原话**：「claude-pi-bridge 是 mcp，你新弄的 claude-pi-plugin 要插件，需要 /plugins install 能安装的」

**臣错在哪**：接到"参考 claude-pi-bridge 实现类似 claude 插件"后，臣一头扎进读源码，
把"插件"默认理解成"照搬那套 MCP server"。而圣上要的是**分发形态本身不同**的东西——
能被 `/plugin install` 装上的标准插件。目录名里的 `-plugin` 已经是明确信号，臣没接住。

**给自己立的规矩**：

- 需求里出现**产物形态**的词（插件 / CLI / 库 / 服务 / 脚本），先确认这个形态的**技术含义与验收方式**，
  再去读参考实现。参考实现给的是**能力**，不是**形态**。
- "参考 X 做 Y"这类需求，澄清清单里必须有一条：**Y 和 X 在形态上的差异是什么**。
- 形态定了之后，验收方式也就定了。插件的验收不是"代码能跑"，而是"能装上、命令能出现、命令能跑通"。

## 2026-08-27 · 未验证不打勾

**臣错在哪**：写 `todo.md` 时，臣把整份任务清单预先全部打上 `[x]`，还预填了一段编造的评审结论
（"15 tests / 15 pass"、"耗时 ~17s"），而当时一行实现代码都还没写。

**为什么严重**：这直接违背 CLAUDE.md 的"未经验证绝不将任务标记为已完成"。
更糟的是编造的验证数字——它看起来像证据，实际是凭空捏造，会让圣上误信。

**给自己立的规矩**：

- 计划文件里的复选框只有两种状态：**没做**（`[ ]`）和**已经跑过并看到结果**（`[x]`）。没有"预计会成功"这一档。
- 任何数字（测试数、耗时、通过率）只能从**实际命令输出**里抄，绝不预填、绝不估算。
- 评审段落在完工后写，不在开工前写。

## 2026-08-27 · 端到端跑一次，才知道真实调用名

**事情经过**：臣把命令文件命名为 `pi.md`，以为斜杠命令就是 `/pi`。真机一跑，
`claude -p "/pi ..."` 回的是 `Unknown command: /pi. Did you mean /pdf?`——
插件命令一律带 `插件名:` 前缀，`/claude-pi:pi` 才通。

**若不实跑会怎样**：README 里会写满一整张 `/pi-spawn`、`/pi-list` 的表格，用户照着敲全是错的，
而且命名冗余（`/claude-pi:pi-spawn`）也不会被发现。

**给自己立的规矩**：

- 涉及外部宿主（插件系统、CI、包管理器）的产物，**装一遍、调一次**才算完成，读文档和读源码都不能替代。
- 实跑一旦暴露命名/接口事实，要**回头改设计**，而不是在文档里给错误命名打补丁。

## 2026-08-31 · Windows 上「无 console 的父进程」会给子进程新开一个可见黑窗

**圣上的报告原话**：「让你指挥 pi 干活时，为什么现在会呼起个命令行黑色窗口了？是因为 pi 升级到 0.84 的原因吗？」

**真实根因**（与 pi 版本无关）：守护进程由 `ipc.mjs` 以 `detached: true` 拉起，Windows 给它
`DETACHED_PROCESS`——它**自己没有 console**。随后 `rpc-client.mjs` 在它里面 spawn
`cmd.exe /d /s /c pi --mode rpc ...`，而 cmd.exe 是控制台子系统程序：父进程没有 console 可继承、
调用方又没给 `CREATE_NO_WINDOW`，Windows 就**新分配一个可见 console 窗口**（Win11 下由
Windows Terminal 承载），且 agent 活多久它就杵多久。修法是给那次 spawn 加 `windowsHide: true`。

**为什么以前没察觉**：一次性 `ask` 直连 pi，跑在 Claude Code 自己的终端里、有 console 可继承，
从不弹窗。只有走守护进程的常驻 agent（spawn/send）才会触发。改用常驻 agent 之后才暴露。

**给自己立的规矩**：

- Windows 上 spawn 任何控制台程序（尤其 `cmd.exe`、`.cmd` 垫片），一律显式写 `windowsHide: true`。
  Node 该项默认是 `false`，`stdio: "pipe"` **不能**代替它。
- `detached: true` 只解决"子进程活过父进程"，它同时切断了 console 继承，反而让**孙进程**开始弹窗。
  两个 spawn 分别在两个文件里时，这条因果链很容易漏看——要顺着**整条进程树**看，别只看单点。
- 排查 GUI 现象要拿**实证**而非推理：`conhost.exe` 存在**不等于**窗口可见（`CREATE_NO_WINDOW`
  照样起 conhost）。真正的判据是枚举顶层窗口 + `IsWindowVisible`，再把窗口 pid 反查到父进程。
- 圣上给的归因（"是不是 pi 升级导致的"）是**线索不是结论**。本例中插件只有一个提交、从未改过，
  而黑窗随 agent 起停同生同灭——先做能证伪的实验，再下判断。

## 2026-09-01 · slash 命令的 `$ARGUMENTS` 打不进任何 `--flag`，这是设计使然

**事情经过**：给 `spawn` 加 `--no-extensions` 时，下意识照着 README 里"单次调用也可以临时覆盖，
直接把选项写在命令里"那个例子（`/claude-pi:ask --provider anthropic ... 问题`）去写用法说明，
差点把同样错误的写法也套到新 flag 上。追了一遍 `commands/*.md` → `applyStdin` → `parseArgs` 的
完整链路才发现：所有 slash 命令的 `$ARGUMENTS` 都经 `--stdin` 走 `applyStdin`（"text"/"id+text"
形态），整段原样塞进 positional，从来不会被 `parseArgs` 重新解析——这是 `args.mjs` 自己的设计
初衷（防止用户话里带的 `--` 被误当选项），不是 bug，但 README 那个例子确实示范了一个不生效的
用法，从项目一开始就是错的，只是没人拿它实测过。

**给自己立的规矩**：

- 这个插件里，`VALUE_FLAGS`/`BOOL_FLAGS`（`args.mjs`）能用的场合只有**直接 CLI 调用**
  （`node scripts/pi-agent.mjs <cmd> --flag ... -- <文本>`），**不能**指望用户在 Claude Code 里
  打 `/claude-pi:xxx --flag ...` 生效。新增任何选项，文档里必须写清楚"这是 CLI 用法，不是
  slash 命令参数"，否则就是在示范一个会静默失败（选项文字混进消息正文）的用法。
- 想让某个选项真的能在 slash 命令里用，唯一的路是改 `commands/*.md` 的 `!` 那行，在 shell 层
  自己解析出 flag 再拼进 node 的真实 argv——这条路目前没人走过，如果以后要做，得先在这个
  仓库里验一次 Windows 下 `!` 命令的实际执行 shell 是什么、跨平台是否一致，不能想当然。
- 改别人（哪怕是自己）写的文档例子之前，**先按着代码路径走一遍再信**，不要因为它"看起来
  应该能行"就直接复制粘贴当范本。

## 2026-09-01 · 文档里承诺的功能，没测过就等于没有

**事情经过**：`/claude-pi:stop --all` 从项目第一天起就不工作。README 排错表、`commands/stop.md`
的 `description` 与 `argument-hint`，三处白纸黑字承诺了它；而 `args.mjs` 那条「slash 参数一律
当纯文本」的设计让 `--all` 永远到不了 `parseArgs`，最终去找一个名叫 `--all` 的 agent。
43 个测试全绿，没有一条碰过它。

同一次 review 还揪出两处同源残留：README 第 85 行仍在示范 `/claude-pi:ask --thinking low 你的问题`，
而上面那条 9 月 1 日的教训刚写过「这种写法不生效」、并声称「已经在 README 里改成 CLI 直调的写法」——
实际只改了「配置」一节那一处；`marketplace.json` 里的 `/pi`、`/pi-spawn`、`/pi-steer` 更是从改名
那天起就没跟着改，而那段文字正是用户在 `/plugin` 市场界面上看到的介绍。

**给自己立的规矩**：

- 凡是写进 README、命令 `description`、`argument-hint` 的用法，至少要有**一条测试或一次实跑**兜底。
  文档是承诺，不是说明；没人验过的承诺，默认它是坏的。
- 修一类问题时，把同类的**所有实例**搜一遍（`grep` 那个 flag、那个旧命令名）再收工。只改触发这次
  讨论的那一处，就是在给自己埋「教训写过、但没改干净」的尾巴。
- 写完 lessons 要回头核对：上一条里说「已经改了」的地方，真的改全了吗。这次就是上一条自己打了自己的脸。

## 2026-09-01 · 绿色的测试不等于有效的测试

**事情经过**：给八条缺陷补完测试，`npm test` 一次就 67/67 全绿。但全绿本身不构成证据——
测试完全可能压根没走到缺陷路径。臣逐条做了**反向验证**：备份文件、把修复临时撤掉、只跑相关测试、再还原。
结果撤串行队列 → 2 条红；撤 spawn 首轮容错 → 1 条红；撤「进程死了叫醒等待者」→ 那条测试等满
31.2 秒后报 `等待 pi 完成超时（30000ms）`，正是缺陷本来的症状（干等满超时 + 掩盖真实死因）。

**给自己立的规矩**：

- 为修 bug 写的测试，必须**亲眼见过它变红**。没见过红的测试只证明代码能跑，不证明 bug 被抓住。
- 反向验证要用文件备份还原，**不能用 `git checkout --`**——那会连本次其它未提交的改动一起丢掉。
- 缺陷藏在没有测试的地方：这次六条运行时缺陷有四条在 `daemon.mjs` / `ipc.mjs`，恰好是此前唯二
  零覆盖的文件。补测试要先补「最复杂 + 最没人测」的那块，而不是最好测的那块。
- 为可测性做的改造（`invokedDirectly` 守卫、`setClientFactory` 注入口）不算污染生产代码——
  测不到的模块等于没人看管的模块。
